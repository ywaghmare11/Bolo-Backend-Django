## 2026-08-23 (3)

- `[STD]` **Planning: Phase 15 — Platform Admin Console (`ROADMAP.md`), no code this session.** Corrects the mental model `PlatformAdmin` was built against in 2026-08-23 (2): `PlatformAdmin` isn't Integrate18's (the vendor's) own tool — it's AIBIGO's (the client's) operator console for onboarding *their* customers (colleges/CA firms) as `Tenant` rows. Standard B2B2C/operator-reseller SaaS shape (Shopify Plus + agencies, white-label LMS vendors, etc.), three access tiers not two: Django's built-in `/admin/` (vendor/infra, free from Django) → `PlatformAdmin` (AIBIGO's operator team) → `TenantMembership.role_level` (each tenant's own internal roles, unchanged since Phase 1).
  - **15a — RBAC on `PlatformAdmin`**: a `role` field, scoped down to `SUPER_ADMIN` only for now (explicit user decision — AIBIGO has one real operator today, add more roles when they actually need the split) — but the permission-class factory (`HasPlatformAdminRole`, mirroring the existing `HasOrgRole` factory exactly) gets built now so a second role later is a one-line change, not a refactor.
  - **15b — un-defers `AuditLog` wiring for `PlatformAdmin` actions**, originally scoped out in 2026-08-23 (2)'s build. Re-scoped in because the corrected model changes who's accountable: once it's AIBIGO's own team creating tenants and adding/removing members (not Integrate18's), "who did what, when" is a real requirement, not nice-to-have. Needs the generic audit middleware extended with a second actor-resolution path for `admin_token` (`apps/common/audit_middleware.py` currently only decodes the tenant-user `token` cookie) — `AuditAction.TENANT_CREATED`/`MEMBER_ADDED`/`MEMBER_REMOVED` already exist in the enum, this is config-table wiring, not new schema.
  - **15c — multi-format bulk import** (Excel/CSV/JSON, `pandas`-based, one shared parse→normalize→validate→upsert pipeline rather than three parallel ones) — expanded from the Excel-only version the original `api-spec.md` §22 contract documented, adding CSV per direct request. Edge cases specified in the plan: encoding fallback (`utf-8-sig`→`latin-1`), header normalization, per-row rejection (never fail a whole batch on one bad row), duplicate-email-within-file handling, chunked transactions with file/row caps, and CSV/Excel **formula-injection** neutralization (a real, often-overlooked security issue when untrusted cell content might ever be re-exported).
  - **15d — operator dashboard, decided to build inside `bolo-web`, not a separate app** — reconsidered from an initial "separate app for isolation" recommendation after weighing it against this project's actual scale (one client, small team): the real security boundary is server-side (`admin_token` validated on every request) regardless of which frontend calls it, so a separate app would mainly duplicate design-system/API-client/query-setup work for marginal gain. Plan: a `/platform-admin/*` route branch as a sibling to (never nested under) tenant routing, its own `PlatformAdminPrivateRoute`, a new `GET /platform-admin/auth/me` endpoint for session checks, code-split so tenant users never download the admin bundle. `admin_token`/`token`/`refresh_token` already coexist in one browser without collision by original design (different cookie names, different JWT shapes) — no new backend work needed for that part.
  - Frontend ownership: user's call, undecided as of this entry — pending a follow-up decision on whether Claude builds the `bolo-web` pieces too or just the API contract for a teammate to build against.

- `[BE]` `[INFRA]` **AI Nudges** (`apps/notifications`) — `GET /nudges`, `POST /nudges/:id/skip`, `POST /nudges/skip-all` (`docs/api/api-spec.md` §11) plus the two recurring Celery beat sweeps that feed it. ROADMAP.md Phase 8's last remaining piece, explicitly flagged as out of scope in the two immediately preceding sessions (`changelog.md` 2026-08-12 (2)).
  - **`docs/api/api-spec.md` §11 has two contradictory `GET`/`POST /nudges` sections left in the same file** — an older one (~line 1487, headed "2026-07-06 redesign") still has Subtask/StickyNote/Broadcast in entity scope, `409 SKIP_CAP_REACHED`/`409 LAST_CHANCE_BLOCKING` rejections, and `ACCEPT_TASK`/`MARK_COMPLETE`/`VIEW_BROADCAST` actions — all superseded by the 2026-07-13 client-directed narrowing documented in `domain-model.md` rows 8c/8d and `open-questions-web-v1.md`'s Section 18 closing note ("Superseded 2026-07-13"). Built against the **earlier-in-file, more-recently-worded** section (~line 1351) instead, which matches the current `domain-model.md`/open-questions state: Task-only, skip always succeeds (no cap rejection, no blocking), feed capped at 5. Flagging this doc contradiction explicitly since api-spec.md's own section ordering doesn't reflect recency here, unlike every other doc-staleness call in this project's history so far.
  - **`NudgeSkipCounter` model/migrations already existed**, ported untouched since the Phase 1 model scaffold (`apps/notifications/models.py`, migrations `0001`–`0003`) — this session is the first to build any service/repository/view/sweep logic on top of it. Schema already matched the current scoped-down shape (`entity_type`/`entity_id`/`nudge_kind` unique triple, `skip_count`, `escalated_at`, `last_shown_at`, no `user_id`) — no new migration needed.
  - **`apps/notifications/nudge_rules.py`** (new) is the single source of truth for nudge eligibility — `classify_followup(task)` and `due_proximity_bucket(task)` — shared by both the Celery sweeps (deciding whether to fire a *new* notification) and `NudgeService` (re-validating an *existing* unread one against current state on every `GET /nudges` call, never trusting what was true when it fired). Re-running `classify_followup` fresh is also what makes "Add Comment resolves the Follow-up nudge" work with zero special-casing — once the assignee's own comment becomes the latest one, the function naturally returns `None`. `due_proximity_bucket` doesn't look at comments at all (it's pure status/due-date/acceptance), so Due-Proximity's own documented "Add Comment resolves it for this cycle" fix needed a separate `resolved_by_comment_since(task, notification.created_at)` check, applied only at `GET /nudges` re-validation time, not at sweep-firing time.
  - **Follow-up (`AI_NUDGE_FOLLOWUP`, `apps/notifications/tasks.py:ai_nudge_followup_sweep`)**: every 6h, no office-hours gate, 2 assignee-only conditions (accepted-no-progress-since / assigner-posted-last-and-assignee-owes-reply), no cap, no escalation — skip counter tracked for rotation only. The sweep now also `get_or_create`s the `NudgeSkipCounter` row at fire time (not just Due-Proximity's sweep) so `last_shown_at` has somewhere to be written before the item is first ever read — a real bug caught by a rotation test that silently no-op'd against a row that didn't exist yet.
  - **Due-Proximity (`AI_NUDGE_DUE_PROXIMITY`, `ai_nudge_due_proximity_sweep`)**: every 3h, no office-hours gate, Task-only, already-accepted + due-today-or-overdue. Cap 3 (due-today) / 1 (overdue) on the **same** counter row regardless of which bucket is currently active — a task that's skipped twice while due-today and then rolls into `OVERDUE` immediately re-evaluates against the stricter cap-1 threshold on the very next tick, which is a deliberate reading of "same `nudge_kind`, cap depends on current bucket" rather than resetting the counter on a status transition. **Escalation is real and independent of whether a fresh routine notification fires that tick**: `skip_count >= cap` + `escalated_at IS NULL` + task hasn't reached `DONE_A` → one-time in-app+email to the assigner, guarded by `escalated_at` so it never repeats; a task reaching `DONE_A` naturally drops out of the sweep's own query (`status__in=(IN_PROGRESS, OVERDUE)`), matching "no escalation past DoneA" with no extra check needed.
  - **Cross-type dedup (`domain-model.md`'s W84 "cooldown window", never given an exact value upstream — W74: "hardcoded constant, sensible default chosen at implementation time")**: implemented as "don't fire a new AI Nudge notification for this recipient+entity while an earlier unread one already exists," rather than a fixed elapsed-time window — the earlier notification is itself the cooldown, and it clears as soon as the user sees/resolves/skips it or the entity condition stops holding. Documented as a judgment call, same as this project's other W74/W75-style "no exact value specified, picked a sensible default" resolutions.
  - **Explicitly not built, flagged not silently dropped**: `domain-model.md`'s "first-login-of-the-day fast-track" (bypass the interval gate once for a user who logged in today but hasn't seen an AI Nudge yet) — that nuance was designed for the *original* Node backend's single continuous 15-minute-tick sweep with internal per-user elapsed-time gating. This project instead follows its own already-established pattern (`task_due_proximity_sweep`, `sticky_note_reminder_sweep`) of one fixed Celery beat crontab per sweep type, where Beat's own schedule already *is* the interval gate — the fast-track concept doesn't map cleanly onto that shape, and retrofitting a parallel gating mechanism just for this one nuance wasn't judged worth the complexity here.
  - **Feed composition** (`NudgeService.get_feed`): reads the caller's unread `AI_NUDGE_*` notifications, dedupes by `(entityId, type)` keeping only the newest (older duplicates silently marked read), re-validates each remaining row against current state (stale ones marked read and excluded), then composes: Due-Proximity fills up to 5 slots ordered by `Task.priority` (P1 first), Follow-up fills any remaining slots also priority-first then oldest-`last_shown_at`-first (nulls/never-shown first) for rotation. `last_shown_at` only updates on Follow-up items that actually make the cut, which is what makes the rotation self-correcting.
  - **`POST /nudges/:id/skip` re-derives `nudge_kind` from current task state rather than storing it** — `Notification` (ported field-for-field from `schema.prisma.reference`) has no spare column for it, and the "always trust current state, never what was true when it fired" philosophy already established for `GET /nudges` extends naturally here. Always succeeds (2026-07-13 — no `409` cap rejection); if the underlying condition no longer holds by the time skip is clicked, the notification still resolves but nothing increments. `POST /nudges/skip-all` reuses `get_feed`'s exact composition (whatever's "currently shown") and skips each item in turn.
  - **Not audited** — no `NUDGE_*` `AuditAction` values exist in the schema (checked via grep before deciding, not assumed), same call as Labels/Search.
  - **Tests**: new `apps/notifications/tests/` package (didn't exist as a package before — converted from the unused Django-default `tests.py` stub, matching every other app's convention), 37 tests across `test_nudge_rules.py` (pure classification logic), `test_nudge_sweeps.py` (both sweeps, cross-type dedup, escalation cap/guard/no-repeat), and `test_nudges_api.py` (feed shape, priority ordering + 5-item cap, stale-condition auto-resolve, comment-resolves-due-proximity, dedup, Follow-up rotation, skip/skip-all, cross-user 404). Full suite: 231 tests, all green; `ruff check` clean on every touched file (pre-existing unrelated lint issues in untouched files left as-is).

## 2026-08-12 (2)

- `[BE]` **Due-date reminder sweep** — closes the gap flagged (but explicitly not built) in the Sticky Notes and Global Search sessions: `TASK_DUE_TODAY`/`TASK_DUE_TOMORROW`/`TASK_OVERDUE` (`docs/api/api-spec.md` §11, row 8) and `StickyNote`'s `REMINDER_FIRED` were never dispatched anywhere — only the sticky-note retention-delete job existed. ROADMAP.md Phase 8's remaining piece.
  - **`apps/tasks/tasks.py:task_due_proximity_sweep`** (new, daily Celery beat job, `crontab(hour=7, minute=0)`) — scans `OPEN`/`IN_PROGRESS` tasks and: notifies (in-app + email) for tasks due today or due tomorrow, and transitions `OPEN`/`IN_PROGRESS` → `OVERDUE` (+ notifies) for tasks whose due date has fully passed. **Fires to both the assignee AND the assigner** — `domain-model.md`'s Notification Events table (row 8, the more recently reconciled source) says both parties; `api-spec.md` §11's older per-type table says assignee only, same kind of inline-table-vs-corrected-table call as the Subtasks/Sticky Notes/Broadcast Notices sessions' earlier fixes.
  - **`OVERDUE` was a real `TaskStatus` enum value nothing ever actually set** — grepped before assuming, confirmed no code path transitioned a task into it. This sweep is what makes it reachable for the first time, which also meant a documented business rule was a **latent, never-yet-reachable bug**: "an `OVERDUE` task auto-transitions back to `OPEN`/`IN_PROGRESS` if its due date is edited to today-or-later" (`CLAUDE.md` Business Rules) had no implementation in `TaskService.update_task`. Fixed in the same pass — reverts to `IN_PROGRESS` if the task was already accepted, `OPEN` otherwise, mirroring `accept_task`'s own forward transition. Regression-tested both directions.
  - **One-shot guards are real, persisted DB state, not a cache/TTL** — new `Task.due_today_notified_at`/`due_tomorrow_notified_at` (nullable datetime, migration `0007`) and `StickyNote.reminder_fired` (boolean, migration `0005`). Chosen over a Redis-keyed guard (unlike, say, Evidence's ephemeral pending-upload cache) because "was this notification already sent" is a durable business fact worth surviving a worker restart and being visible in the DB, not a short-lived coordination detail. `TASK_OVERDUE` needed no equivalent field — the status transition itself is the one-shot guard, since an already-`OVERDUE` task no longer matches the sweep's `OPEN`/`IN_PROGRESS` query. Editing a task's `due_date` resets both `_notified_at` flags (a new due date is a genuinely new threshold to cross) — wired into the same `TaskService.update_task` branch as the reverse-transition fix above.
  - **Retry policy per `ROADMAP.md` Phase 8's explicit call-out**: both new Celery tasks (`task_due_proximity_sweep`, and `apps/sticky_notes/tasks.py`'s new `sticky_note_reminder_sweep`) declare `autoretry_for=(SMTPException,)` with exponential backoff, max 3 retries. Safe to retry blindly because of the idempotency design above — a retry after a partial-send failure only reprocesses rows that never got marked notified, never double-sends what already succeeded.
  - **`REMINDER_FIRED` swept every 15 minutes** (`crontab(minute="*/15")`), not once daily like the retention-delete job — a sticky note's `dueAt` can land at any time of day and the doc's own wording ("fires once when `dueAt` is reached") implies prompt firing, not next-morning. In-app only, no email channel, per `api-spec.md` §11's Channel column for this type specifically.
  - **Subtasks included, not filtered out** — a `Task` row with `parent_task` set is swept exactly like a main task (no special-casing), consistent with how the rest of this project already treats "a subtask is just another task."
  - **Explicitly not built this session** (flagged, not silently dropped): `AI_NUDGE_FOLLOWUP`/`AI_NUDGE_DUE_PROXIMITY` (the *recurring* skip-cap/escalation nudge system, `GET /nudges`, `NudgeSkipCounter`) is a separate, much larger feature the session's own scoping deliberately excluded — this slice only covers the one-shot due-proximity/reminder notifications (table row 8/13), not the AI Nudge feed (rows 8c/8d).
  - **Tests**: new `apps/tasks/tests/test_due_proximity_sweep.py` (13 tests — due-today/due-tomorrow/overdue notification + idempotency-on-rerun, Draft/DoneD exclusion, the day-boundary edge case of a task due *today* not yet counting as overdue, both directions of the reverse-transition fix, notified-flag reset on due-date edit, subtask inclusion) and 4 new tests in `apps/sticky_notes/tests/test_sticky_notes.py` (fire-once, no-refire-on-rerun, not-yet-due and no-due-date no-ops). Full suite: 194 tests, all green; `ruff check` clean on every touched file.
